# Vitz Music

Личный музыкальный сервис: бэкенд со стримингом, аккаунты по инвайтам, плейлисты и
«понравившееся», веб-админка для загрузки треков. Android-плеер — отдельным этапом.

План целиком: [docs/MUSIC-PLAN.md](docs/MUSIC-PLAN.md).
Развёртывание и автодеплой: [docs/DEPLOY.md](docs/DEPLOY.md).
Выпуск сборок плеера и самообновление: [docs/RELEASES.md](docs/RELEASES.md).

## Запуск локально

Нужен Docker и заполненный `.env`:

```bash
cp .env.example .env
```

Секреты сгенерировать (по одному на каждую переменную `*_SECRET`):

```bash
openssl rand -hex 32
```

Поднять всё, включая сборку образа:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

Админка — `http://localhost:8080/admin`, вход под первым администратором из `.env`
(создаётся при первом старте, если в базе нет ни одного пользователя).

Обратного прокси в наборе нет: локально сервер слушается напрямую, а на боевом сервере
маршрут и сертификат даёт уже стоящий там Traefik — см. [docs/DEPLOY.md](docs/DEPLOY.md).

## Разработка без Docker

Нужны JDK 21+ и ffmpeg в `PATH`. База — в контейнере:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres
```

Затем:

```bash
./gradlew :server:run
```

Переменные окружения по умолчанию рассчитаны на локальную машину
(`jdbc:postgresql://localhost:5432/vitzmusic`, медиа в `./media`), секреты в dev-режиме
подставляются небезопасные — сервер об этом предупреждает в логе и отказывается стартовать
с ними, если `VM_PUBLIC_URL` не `localhost`.

Тесты:

```bash
./gradlew :server:test
```

## Структура

```
shared/   DTO API, общие с Android-клиентом
server/   Ktor: аутентификация, каталог, ингест, раздача, админка
  db/       пул, миграции, помощники JDBC
  auth/     Argon2id, токены, инвайты
  media/    хранилище по SHA-256, подписанные ссылки, раздача с Range, уборка диска
  ingest/   ffprobe/ffmpeg, теги, дедупликация, рендиции
  jobs/     очередь заданий в Postgres
  catalog/  треки, плейлисты, лайки, синхронизация
  admin/    страницы админки (серверный рендер + немного ванильного JS)
```

## Удаление и место на диске

Удаление трека из админки — мягкое: строка остаётся с `deleted_at` и служит надгробием, по
которому плеер на синхронизации понимает, что трек надо убрать и у себя. Стереть строку сразу
нельзя — телефон, который в этот момент был вне сети, никогда бы об удалении не узнал.

Файлы сносит фоновая уборка (`media/MediaGc.kt`), она же ходит по хранилищу и подчищает
бесхозное — следы упавшего ингеста, обложки без владельца, пустые альбомы и артистов:

- трек лежит в «Корзине» `VM_TRASH_RETENTION_DAYS` дней (по умолчанию 30), оттуда его можно
  вернуть или стереть сразу кнопкой «стереть насовсем»;
- по истечении срока строка и файлы удаляются с диска;
- файл уходит, только если на него не ссылается никакой другой трек: хранилище адресуется
  хешем содержимого, и побайтовые копии у треков общие;
- файл без ссылки из базы сносится не раньше чем через `VM_GC_ORPHAN_GRACE_HOURS` часов —
  ингест кладёт файл в хранилище раньше, чем строку в базу, и без отсрочки уборка сносила бы
  файл прямо из-под работающей загрузки.

Проход идёт раз в `VM_GC_INTERVAL_MINUTES` минут (`0` выключает фон целиком), а кнопка
«Прибраться сейчас» на вкладке «Корзина» запускает его руками.

## Сквозная проверка

Скрипт проходит весь путь: вход в админку → загрузка файла → ингест → инвайт → регистрация
пользователя → каталог → стрим с `Range` → плейлист, лайк, синхронизация.

```bash
./scripts/smoke.sh http://localhost:8080 admin@example.com <пароль> путь/к/треку.mp3
```

Он создаёт в базе пользователя, плейлист и инвайт — гонять только на тестовом стенде.

## Проверка руками

После `docker compose up -d`:

```bash
curl -fsS http://localhost/healthz
```

Дальше — `/admin`, вход первым администратором, вкладка «Загрузка»: перетащить пару mp3
и дождаться в очереди статуса `done`. Трек появится в «Каталоге», а ссылка из
`GET /api/v1/tracks` проигрывается в браузере и перематывается.
